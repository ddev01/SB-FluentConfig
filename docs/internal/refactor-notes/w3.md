# W3 — Settings identity and defaults seeding

## What changed

- Explicit menu id (`[a-z][a-z0-9_]*`) is persistence and window-registry identity. Window title is a label.
- `Fc.Open` / `Create` / `LoadSettings` / `HasSavedSettings` / `KeyFor` / `{id}_settings` / `{id}_data` take the id, not the title.
- Deleted `MigrateLegacySettingsKey`, `LegacySettingsKeyFor`, and the `FluentConfig_Settings_{title}` path (no users to protect; also drops a CPH read from those hot paths).
- Throwaway `FluentConfig/scripts/RenameSettingsKeys.ps1` copies `{old_slug}_settings|_data` → `{new_id}_*` in a globals JSON dump. Delete after use.
- `TryBeginOpen` treats a null placeholder as reserved. `Create().Show()` uses the same reservation as `Fc.Open`.
- `CollectDropdown` empty-options branch seeds `defaultByValue` onto `valueSaveKey` (pair) or `saveKey` (else). Does not seed a display string.

## 0.2 breaking-change bullets

- `Fc.Open(cph, title, version, build)` → `Fc.Open(cph, id, title, version, build)`. Same extra `id` argument on `Create`, `ShowOrFocus`, `LoadSettings`, `Get/SetSetting`, `SaveSettings`, `HasSavedSettings`, `DataKeyFor`, `Load/SaveData`, `Get/SetData`, `SettingsKeyFor`, `KeyFor`.
- Menu id must match `[a-z][a-z0-9_]*`. Titles like `"Foo"` / `"Foo!"` / `"Foo "` are no longer valid identity keys (slug collisions are unreachable).
- Settings globals are `{id}_settings` / `{id}_data`. The old `FluentConfig_Settings_{title}` key is not read. Use `RenameSettingsKeys.ps1` for owner menus, then delete the script.
- `Fc.AlreadyOpened` default id is `fluentconfig` (the old `"FluentConfig"` default is not a legal id).
- Considered and rejected: putting the version in the key (orphan-on-bump, same bug as rename). Considered and rejected: a new global per menu (CPH must stay scannable as `{id}_settings`).
