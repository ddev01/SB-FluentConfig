================================================================================
1. WHAT THE PRODUCT IS
================================================================================

FluentConfig is a Streamer.bot plugin DLL (.NET Framework 4.8.1, net481).

- Extension authors write a fluent C# DSL describing a settings menu.
- The Host serializes a camelCase JSON *schema* over a WebView2 postMessage bridge.
- A Svelte 5 + TypeScript + Tailwind + Vite app renders that schema inside a thin
  WPF window hosting WebView2.
- Persistence is Streamer.bot CPH global variables (CPH.SetGlobalVar / GetGlobalVar).

An older WPF widget-tree UI was deleted because it was slow, dated and clunky.
The rewrite locked in: Svelte 5 + TS + Tailwind, schema on the wire, and no
WPF/UI-framework objects crossing the host/web boundary.

The author is currently the only consumer, so breaking the author-facing API is
allowed, but this is intended to become a library other extension authors use.

NON-NEGOTIABLE CONSTRAINTS (apply to every workstream):
- No WPF or UI-framework objects on the wire.
- camelCase JSON on the wire.
- WebView2 is never bundled and never NuGet-referenced. Compile against
  Streamer.bot's own copies with Private=False. A different version in dlls/
  causes FileLoadException inside Streamer.bot.
- Layout and visibility are evaluated client-side. Flipping a toggle must not
  remount the tree or round-trip the host.
- JSON never carries raw Tailwind class strings (Tailwind v4 has no usable
  safelist for dynamic class names). The host resolves tokens to CSS.
- LangVersion is "latest" but the runtime is net481: default interface methods
  are FORBIDDEN (TypeLoadException in Streamer.bot). Author-facing signatures
  stay C# 7-shaped because consumers paste code into Streamer.bot's in-app
  compiler.
- docs/internal/CODE_REVIEW_AND_REFACTOR_PLAN.md is a HISTORICAL audit dated
  2026-08-05. Most of it already shipped. Treat as background only. Do NOT
  re-execute it as a checklist.

3. LOCKED DECISIONS - DO NOT RELITIGATE
================================================================================

These were decided by the repo owner during research. They are constraints.

3.1 Cold-start optimization is OUT OF SCOPE.
    The historical "large alerts menu took ~10s cold" number belongs to the
    DELETED WPF widget tree, not this architecture. Every archived baseline in
    docs/performance/baselines/ is framework-sized: complete cold totalMs ~1282,
    warm ~276. The cold-warm delta is first-HWND JIT plus WebView2 process spawn,
    which is a tax, not a bug. Action: add a measurement fixture only (S5 step 8).

3.2 The colour palette is correct and deliberate. DO NOT change
    --color-fc-accent, --color-fc-glow, --fc-network-rgb, or any theme token in
    web/src/app.css. (Note: the accent is #00a86b light / #00c47a dark. #00ffa3
    exists only as a dead fallback literal at NetworkBackground.svelte line 65.)
    The ONLY colour change permitted in this whole plan is the stock-Tailwind-blue
    button fallback described in S4A step 8.

3.3 "ddev01/SB-FluentConfig" STAYS in FluentConfigUi.cs line 52 and in
    examples/deployment/01_DllCheck.cs line 25. Owner's explicit call. Do not
    placeholder it. (The machine path in Redeploy.ps1 is a SEPARATE, in-scope bug.)

3.4 There are no external users. Clean breaks are acceptable. Do NOT build
    permanent migration machinery. A single-use throwaway script is correct.

3.5 Empty-versus-none model is settled:
      - key ABSENT   = "never touched"      -> schema default may be used
      - key === ''   = "explicitly none"    -> schema default must NOT be used
      - key = value  = that value
    No protocol change. Merge-save stays delete-free. (This matters because
    SettingsSync.MergeValues cannot delete keys, so any design that requires
    "remove the key" is unimplementable through the current save path.)

3.6 Compile-time option safety is STAGED: runtime guards now, phantom-typed
    chain later as its own workstream. Do NOT attempt phantom types in this wave.

3.7 All breaking author-facing API changes batch into a single 0.2 release.

================================================================================

Do not spend effort on these. All verified as already shipped:

4.1 "PendingControl silently drops wrong-kind options" - FIXED.
    PendingControl.Options.cs line 10 defines RequireKind, which throws on both
    wrong kind AND Kind.None, and is called by nearly every option setter.
    PendingControlTests locks it (e.g. Password on toggle throws).
    WHAT REMAINS: exactly three ungated options - Hint (line 22), the ShowWhen /
    ShowWhenNot family (lines 79-134), and Size (line 136). Plus MaxSelected /
    DefaultIndex / DefaultIndices pass the toggle guard but are only read inside
    the exclusive branch of BuildToggle, so they are silent no-ops on a plain
    toggle.

4.2 "Slider Range(double) possibly ignored" - FIXED, and deliberate.
    PendingControl.Build.cs lines 73-78 round double ranges on purpose so
    .Range(0.0, 100.0) works. Tested.

4.3 "Pill optimistic UI before RPC" - FIXED. Mutation now happens after RPC
    success. Only the `draft` input value is still cleared too early.

4.4 "values.patch makes the form look dirty" - FIXED. app.svelte.ts lines 374-385
    dual-write into both values and savedValues.

4.5 "update.stage can download arbitrary URLs" - NOT TRUE, guarded three ways.
    FluentConfigSession.Rpc.cs lines 289-303: the URL must exactly equal
    _pendingUpdate.DownloadUrl, must pass GitHubUpdater.IsAllowedDownloadUrl
    (https + GitHub download hosts), and DownloadToFile enforces a 64 MiB cap
    plus an MZ/PE header check. Furthermore the notify-only check path always
    sets DownloadUrl = null (GitHubUpdater.cs lines 185-194, 286-295), so the RPC
    CANNOT SUCCEED in production at all. It is dead code wearing a security
    guard - delete it from the wire (S5 step 2).


================================================================================
5. VERIFIED FINDINGS THAT DRIVE THIS PLAN
================================================================================

Each of these was read and confirmed in source. Severity ordered.

5.1 [HIGH - SILENT DATA LOSS] Native close discards unsaved edits after 60s.
    HostBridge.SendRequest (HostBridge.cs line 84) defaults timeoutMs = 60000 and
    arms a DispatcherTimer that resolves the pending task with null.
    FluentConfigSession.Lifecycle.cs lines 63-68:
        // Null = timeout / error / detach. Prefer closing over a permanently stuck X.
        if (parsed == null) { FinishNativeClose(allowClose: true, ...); return; }
    So: unsaved edits -> click X -> discard dialog appears -> user reads the diff
    for a minute -> window closes and throws the edits away.
    CompletePendingResponse (line 169) also maps an error reply to null, so a
    web-side exception in the dirty check has the same effect.

5.2 [HIGH - SILENT] Framework version compares as 0.1.0.0.
    Host.csproj does not disable SourceRevisionId, so
    FluentConfigBuildInfo.FrameworkVersion is
    "0.1.0-beta.2+9e559636beae039dea66e7689cac08abed5a3886".
    GitHubUpdater.cs line 466: Normalize = Regex.Replace(v, @"[^0-9.]+", "").
    Trace: "-beta." collapses to "." giving "0.1.0.2", then "+" is deleted and
    the hash's digits concatenate directly onto that 4th component with no dot
    separator. Result: a ~25-digit 4th part. IsNewer (lines 469-481) does
    int.TryParse, which OVERFLOWS, and the loop substitutes 0.
    Net effect: installed beta.2 reports as 0.1.0.0 to every comparison, so an
    extension gating on minFluentConfig "0.1.0-beta.2" is blocked with a popup by
    a DLL that satisfies it. No error, no log.

5.3 [MEDIUM] window.close ignores alreadyConfirmed:false.
    RpcMethods documents alreadyConfirmed as the flag that skips the round-trip,
    but FluentConfigSession.Rpc.cs lines 338-353 always calls
    _window.CloseAllowed(). Native X is guarded; this path is not.

5.4 [MEDIUM] TryBeginOpen reserves nothing.
    FluentConfigWindowManager.cs line 66 writes OpenWindows[title] = null as a
    "placeholder reservation", but the already-open branch at line 50 requires
    window != null. So a second opener during the first one's build() +
    Schema.Build also gets true and creates a second session. The comment
    describes concurrency control the code does not implement.

5.5 [MEDIUM] Author refresh callbacks run synchronously during schema build.
    PendingControl.Build.cs lines 192-194:
        // Refresh-only dropdowns (no static .Options) start empty unless seeded here.
        if (opts == null || opts.Count == 0)
            opts = refreshFn();
    So every .Refresh(() => Fc.TwitchRewardGroups(CPH)) dropdown without static
    .Options makes a synchronous Streamer.bot / Twitch call on the schema-build
    path before first paint, once per dropdown, serially.
    SECOND-ORDER BUG: when that seed returns EMPTY (Twitch offline, no rewards),
    DropdownControl.svelte lines 23-27 refresh on mount because options.length is
    0 - and App.svelte's {#key activeSection.id} remounts the tab, so the RPC
    re-fires on EVERY tab switch, forever. One fix addresses both.

5.6 [MEDIUM - USER VISIBLE] Repeatable rows remount on every keystroke.
    RepeatableRowsControl.svelte lines 62-69:
        /** Stable-ish key for {#each} so remove/reorder doesn't remount the wrong row inputs. */
        function rowKey(row, index) {
          const fingerprint = Object.keys(row).sort().map(k => `${k}=${String(row[k])}`).join('|');
          return fingerprint || `row-${index}`;
        }
    The key is a fingerprint of the row's EDITABLE values, so typing one character
    changes the key and Svelte remounts the row - losing focus and cursor position.
    The doc comment states the opposite intent.
    DynamicTextboxesControl has the identical bug with `${index}:${item}`.
    CONFIRMED: the control has only addRow / removeRow, no reorder UI.

5.7 [MEDIUM] patchPillItems does not recurse.
    store/app.svelte.ts lines 292-306 only inspects top-level section.children,
    while patchDropdownOptions directly above it (lines 262-290) correctly walks
    groups, pill items and repeatable-rows. So a PillInput nested inside a Grid or
    a WithVisibility block never receives host-expanded items after pill.changed:
    the host replies correctly and the web drops the result.

5.8 [MEDIUM] Window title is doing three separate identity jobs.
    - Storage:       {slug(title)}_settings and {slug}_data
    - Window focus:  FluentConfigWindowManager keys on the RAW title
    - Prefs:         FluentConfig_UpdatePrefs_{raw title}
    - Geometry:      fluentconfig_settings -> windows.{raw title}
    Renaming a window silently orphans settings, update prefs, geometry and the
    discard preference, in three different ways. Slug collisions are also real:
    "Foo", "Foo!" and "Foo " all map to foo_settings.

5.9 [MEDIUM] Deploy script is broken for anyone but one machine, via a commit
    whose message claims the opposite.
    FluentConfig/scripts/Redeploy.ps1 lines 50-52 have exactly one candidate:
        $candidates = @( "F:\Stream\Streamer.bot-x64-1.0.7" )
    Commit 58d04e2, titled "chore(scripts): detect streamer.bot install without
    hardcoded paths", is what DELETED the generic USERPROFILE\Desktop and WinGet
    fallbacks that PACKAGING.md lines 27-35 still document. Host.csproj lines
    41-45 also still resolve a different Streamer.bot version (1.0.4).

5.10 [LOW-MEDIUM] Four overlapping public entry points.
     FluentConfigApp, a class FluentConfig inside namespace FluentConfig, Fc, and
     FluentConfigUi - mostly forwarding to each other (FluentConfigUi.cs lines
     18-392). For a library, this is the first thing a new author trips on.

5.11 [LOW-MEDIUM] PendingControl.Reset() is dead defensive code that looks
     load-bearing. ControlHostBuilder.cs lines 77-83 already allocate
     `new PendingControl(...)` for every control, then BeginX calls Reset on that
     brand-new object. So 55 lines clear 68 fields that are already default. It
     implies a "forgot to reset a new field" hazard that does not exist.

5.12 [LOW-MEDIUM] Key and id collisions are silent.
     SchemaNodeList.cs lines 22-26: TryReserveSaveKey is PER LIST, and every
     nested Grid / visibility group / RepeatFor row / pill template allocates a
     fresh SchemaNodeList. So two points_1 controls in one section can both
     persist into one JSON key. valueSaveKey is never reserved at all.
     RepeatFor splices children onto the parent list without reserving
     (SchemaBuilderHelpers.cs ~line 191). RegisterButtonClick
     (FluentConfigSession.cs lines 105-108) overwrites on duplicate id, and
     btn_ ids are label-slugged, so two .Button("Save") calls collide silently and
     break schema.patch routing. Two Grid("grid-cols-2") both emit id "grid_2".

5.13 [LOW-MEDIUM] RepeatFor can silently generate 100 gated groups.
     RegisterDeclaredRangeIfAny (PendingControl.cs lines 248-258) registers a range
     for EVERY slider unconditionally, and BuildSlider defaults to min 0 / max 100.
     So RepeatFor("volume") on a slider with no explicit .Range materializes 100
     real controls plus 100 gate groups plus 100 seeded default keys. Also
     resolvedMax < startIndex silently emits nothing.

5.14 [LOW] Size() does not merge.
     PendingControl.Options.cs line 151: _sizeHint = hint. So
     .Size("w-fit").Size("col-span-2") keeps only the span, while
     docs/guides/LAYOUT.md says tokens "combine freely".

5.15 [LOW] Dead 'snap' variant across three places.
     lib/dropdownRefresh.ts declares { action: 'snap' } in RefreshDecision but
     resolveDropdownRefresh never returns it (lines 35-39), and DropdownControl
     still has a branch handling it. The keepValues (multi prune) path has no test.

5.16 [LOW] Store reactivity idioms.
     store/app.svelte.ts lines 248-252: setValue deep-clones the ENTIRE values
     blob on every keystroke. Line 63: isDirty is a plain getter running deepEqual
     over the whole blob on every read, not a $derived. PillInputControl.svelte
     lines 41-47 use $effect to synchronize state (documented Svelte 5
     anti-pattern; can loop).

5.17 [LOW] ButtonControl falls back to stock Tailwind blue.
     ButtonControl.svelte line 40: style:background-color={node.color ?? '#3b82f6'}
     That is Tailwind blue-500 inside a green-accented glass UI - the generic kit
     that was explicitly rejected, leaking in through a default.

5.18 [LOW] RepeatableRows deep-clones per render.
     scopedNode(child, index) is called inline in the template, so it deep-clones
     every child of every row on every reactive update.

5.19 [LOW] Docs contradict code in nine places. See S5 step 9.

5.20 [LOW] StartupPerformanceTests.cs is named like a perf gate but builds schema
     only, never touches WebView2, and asserts a 5-second cap that cannot trip.

6. WORKSTREAM STRUCTURE AND WHY
================================================================================

THE CONTENTION PROBLEM
FluentConfigSession is the contended type. Its main partial (388 lines) holds the
builder registries, the Show() pipeline, schema build, AND the values/settings
accessors - so the DSL work, the lifecycle work, and the settings work all need
to edit one file. Same for FluentConfigSession.Rpc.cs (one switch plus handlers
for save, pills, dropdowns, window, updates, perf) and two grab-bag test files
(Phase2HostSmokeTests.cs at 441 lines, PendingControlAndUpdaterTests.cs).

THE SOLUTION
One short SEQUENTIAL stream (S0) carves those files into per-concern partials and
handler files with zero behavior change, so every later stream owns disjoint
files outright. S0 also introduces one indirection seam (SettingsScopeKey) so the
lifecycle stream and the settings stream each change ONE SIDE of the identity
rename without touching each other's files.

DEPENDENCY ORDER (plain text)
    S0  (sequential, first)
     |-- S1  DSL and Builders
     |-- S2  Window lifecycle and close
     |-- S3  Identity, settings and values
     |-- S5  Updater, packaging, protocol, docs
    S4A  Web controls and combobox     (no dependency - start immediately)
    S4B  Web store, shell and pills    (no dependency - start immediately)
    ...all converge on MERGE AND VERIFY

S4A and S4B are web-only and depend on nothing. They run in parallel with S0.
S5 has a host portion that needs S0; its protocol/docs/csproj/script portion does not.

GLOBAL RULES FOR EVERY EXECUTOR
 1. Touch ONLY files your stream owns. If you think you need a file another
    stream owns, STOP and record it in your final report instead of editing it.
    A wrong merge here is silent.
 2. Preserve the reason, not the code. Each step lists an invariant. If your
    implementation satisfies the invariant more simply, do that and say why.
 3. Never violate the non-negotiables in section 1.
 4. Do not add controls, RPC methods, or wire fields the plan does not name.
 5. Update the tests your stream owns in the same change. Both suites must be
    green before reporting done: `dotnet test` (baseline 253) and, in
    FluentConfig/web, `bun test` (baseline 29).
 6. Do not reformat or "tidy" code outside your change. Keep diffs reviewable.

================================================================================
12. WHY THE OBVIOUS SHORTCUTS WERE REJECTED
================================================================================
- Cancelling Window.Closing for the unsaved guard is the classic WPF approach and
  is precisely what blanked the WebView. The SC_CLOSE intercept exists so Closing
  is never raised-then-cancelled.
- Moving the dropdown refresh decision table to the host would require shipping
  the uncommitted web store to the host on every refresh. Empty-until-chosen is a
  UI invariant; it stays next to its test.
- Mounting all tabs would preserve scroll but instantiate every control and run
  every mount-time fetch at bootstrap.
- Sending Tailwind class strings on the wire fails Tailwind v4, which has no
  usable safelist for dynamic names; host-resolved CSS is the correct boundary.
- Per-kind builder classes would restore the WPF-era explosion, where every
  structural method had to be copied onto a dozen types.
- A synthetic row id for each-keys would leak a non-author field into the
  persisted settings blob.
- Full protocol codegen would slow iteration, duplicate the SchemaNodeConverter
  rules, and still miss semantic drift; a snapshot test catches the class of bug
  that actually bites.
- A pre-warmed hidden WebView2 would attack the ~1s cold tax but costs a browser
  process for the whole Streamer.bot session and violates the teardown invariant.
